## 0. 项目叙事（开场 1 分钟，决定面试官往下问什么）

**Q0.1 ⭐ 介绍一下 AgentFlow，重点讲你做了什么**

要点（30 秒版）：
- 一句话定位：对话式 AI 工作流平台，Spring Boot 4.1.1 + JDK 21，不依赖 LangChain 等框架，核心链路手写。
- 已有底座：DeepSeek 对话接入、SSE 打字机流式、多轮会话（MySQL 落库跨重启）、网页控制台。
- 本次升级（重点讲）：完整 RAG 管线——文档上传 → Tika 解析 → 结构感知分块 → 智谱 embedding-3 →
  Redis Stack HNSW 向量检索 → 带引用编号的回答 → 自建评测集驱动调优。
- 收口数字：千块级检索 p95=4ms；评测 40 条 QA，Recall@5 最高 1.000；忠实度 20/20 零编造；陷阱题 3/3 诚实拒绝。

追问：
- **最难的点是哪一步？** → 分块与评测（见第 2、4 部分）。讲"预期的提升没出现，追机制发现是重叠在兜底"的故事。
- **如果重来会改什么？** → ① 先建评测集再写管线（先有尺子再动手）；② embedding 维度调研阶段就锁定，避免"先定维度再建索引"的返工风险；③ 混合检索提前（关键词对报错码类查询明显更优）。
- **和用 LangChain/LlamaIndex 比有什么不同？** → 每一层都是显式决策：分块策略自己实现（结构感知 vs 滑窗是可控对比项）、向量协议直写 RediSearch（知道 PARAMS/TAG/归一化这些细节）、SSE 协议自定义。框架给你速度，手写给你可讲性和可控性——个人项目要的是后者。

## 1. SSE 与会话链路

**Q1.1 ⭐ SSE 和 WebSocket 的区别？为什么大模型对话选 SSE？**
【要点】SSE：单向（服务器→客户端）、基于纯 HTTP、文本协议、浏览器 EventSource 自动重连；WebSocket：双向、独立协议（upgrade 握手）、二进制支持。
对话场景是"一次请求、服务器持续吐字"，不需要客户端向服务器推数据——单向就够。SSE 复用 HTTP 基础设施（代理/网关/鉴权），实现和运维成本都低。
【本项目实证】浏览器 EventSource 只支持 GET，而对话要 POST 带 body——所以用 fetch 手动读 ReadableStream 自己拆帧（这也是能自定义协议的前提）。
【追问】断线重连谁负责？→ SSE 规范有 retry 字段和 Last-Event-ID，自研协议里会话 id 先行，重连后带 sessionId 续接。

**Q1.2 ⭐ 流式接口的错误处理和阻塞式有什么本质区别？**
【要点】分界线：HTTP 状态码只能在"流开始之前"设置。流一旦开始（200 + 响应头已发出），错误只能作为流内事件发（event:error），HTTP 层永远是 200。
【本项目实证】错误事件同时必须记服务端日志（坑8：只发事件不留日志，服务端零痕迹）。上游 401/429 等在 DeepSeekClient 的 onErrorMap 统一翻译成带指引的中文 BizException——阻塞路径走 GlobalExceptionHandler，流式路径的错误事件直接拿到同一段文案，一处翻译两条路径受益。
【追问】怎么区分"流开始前"和"开始后"的错误？→ key 未配置这类前置校验故意同步抛出（能正常返回 HTTP 错误码）；流中的错误走事件。

**Q1.3 SSE 增量为什么要 JSON 编码后再发？**
【要点】SSE 规范规定客户端吃掉 `data:` 后面的一个空格。DeepSeek 的增量自带前导空格（如 " How"），裸发会丢空格 → 单词粘连。JSON 字符串的引号把内容原样包住，空格/换行都不丢，顺带免疫增量内换行破坏帧。
【本项目实证】前端 fetch 解析器里 delta 帧做 JSON.parse。服务端用 `SseEmitter.event().data(json, TEXT_PLAIN)`。
【追问】为什么不用 TEXT_PLAIN 直接发转义后的文本？→ JSON 是现成的、双向可解析、跨帧边界安全的最小方案。

**Q1.4 多轮对话的"记忆"是怎么实现的？LLM 不是无状态吗？**
【要点】LLM API 无状态，记忆 = 每次请求把历史全量带上。存什么和带什么分离：数据库存全部（可审计可回放），发给模型只取最近 20 条（token 成本可控）。
【本项目实证】chat_message 单表按 session_id 分组；会话 id 客户端生成、服务器只认 id 不认人（无状态服务的雏形）。完整回答只在流成功结束后写入历史——半截回答不污染上下文。
【追问】历史越来越长怎么办？→ 三条路：截断（已做，Top20）/ 老消息摘要压缩 / 按相关性检索历史（RAG 思想）。

**Q1.5 HTTP 状态码恒 200、错误码放 body，这个风格好不好？**
【要点】优点：客户端解析统一、错误信息结构化；缺点：网关/监控按 HTTP 状态统计错误率会失真，重试中间件、熔断器都认不出 5xx。这是"前后端联调舒服"与"可观测性"的取舍，生产里建议错误用真实状态码。
【本项目实证】已在 roadmap 坑5 记录，Phase 5 可观测化时回看。

## 2. RAG 管线：解析、分块、嵌入

**Q2.1 ⭐ 画出完整的 RAG 管线，每步做什么**
【要点】上传（multipart，存原件到 data/uploads/docId/）→ Tika 解析（PDF/DOCX/TXT 一套 API）→ 分块（结构感知，块 400 字 + 重叠）→ 批量嵌入（16 条/批 + 内容 hash 缓存）→ 向量库（Redis Stack HNSW）→ MySQL 登记册 → 检索（query 向量化 → KNN top-5）→ 提示词注入（[n] 编号资料）→ 流式回答 + sources 帧。
【追问】哪一步失败会留下脏数据？→ 不会：任何一步失败都中止且不登记文档（登记册最后写）；最坏情况是"原件已存但未入库"，重传即可。

**Q2.2 为什么选 Apache Tika？怎么防伪装扩展名？**
【要点】一套 API 吃掉几十种格式（不引 PDFBox+POI 两套 API），加新格式零代码。模块化引依赖（core + pdf/microsoft/text 三个模块）而不是几十 MB 的 standard 全家桶。
【本项目实证】Tika 按内容探测优先于扩展名——把纯文本改名 .pdf 上传，仍按 text/plain 解析成功（坑22：防伪装靠内容检测，MIME 归一化后进登记册）。
【追问】扫描版 PDF 呢？→ 文字在图片里，抽不出文本 → 明确报"可能是扫描件，需要 OCR，本管线不支持"——诚实失败好过静默空结果。

**Q2.3 ⭐ 为什么分块要有 overlap？块太大/太小分别有什么问题？**
【要点】
- 块太大：一个块混多个主题，嵌入向量语义被稀释（"平均语义"），检索命中后喂给模型的上下文噪音多，还浪费 token。
- 块太小：语义不完整，"主语在上一块"的指代类问题答不了；块数量爆炸，索引开销大。
- overlap：保证跨边界的信息至少在一个块里完整出现，是滑窗式切分的"修补术"。
【本项目实证】默认 400 字 + 15% 重叠。但 C 块评测发现重叠是双刃剑（见 Q4.3）——结构感知分块因为边界本来就落在语义边界上，0% 重叠反而最优。

**Q2.4 ⭐ 结构感知分块是怎么实现的？能脱稿讲吗**
【要点】三步：
1. 行扫描识别标题：Markdown `#`、编号模式（`第X章`、`1.2`、`一、`、`（三）`），外加启发式（短行 + 无句末标点 + 后面紧跟正文，排除纯页码行）；
2. 空行/标题切出段落块，每块带字符偏移和所属标题上下文；
3. 贪心装箱：装不下就收块，新块从上一块尾部按句边界回借 overlap 字符——借的是完整句子不是裸字符；单段超长（PDF 无空行文本常见）按句切分再装箱。
【本项目实证】块元数据带 offset（可溯源）和 heading（来源卡片显示"出自哪个小节"）。踩过的 bug：回借区之后第一个真实块要更新所属小节，否则整篇都挂在文档大标题下（88874d2 修复 + 回归测试）。
【追问】offset 为什么是行级精确、字符级近似？→ 段落内部逐行 strip 过，重叠借入区起点按 lastIndexOf 回溯——溯源够用。

**Q2.5 ⭐ embedding 维度怎么选的？为什么"先定维度再建索引"？**
【要点】embedding-3 支持 256/512/1024/2048。维度↑表达能力↑，但内存（向量数 × 维度 × 4B × 图结构系数）和延迟也↑。选 1024：质量/成本平衡点，与开源 bge-m3 原生维度一致。
"先定维度再建索引"：维度是索引参数（HNSW 的 DIM），建好后改维度 = 所有历史向量作废 + 重建索引。所以配置里的维度和索引 DIM 必须绑定校验。
【追问】为什么不干脆 2048？→ 千块级质量差异感知不到，内存延迟翻倍没有收益；且 1024 是业界甜点位（bge-m3 同款）。

**Q2.6 ⭐ embedding 缓存怎么设计的？为什么 key 要拼上模型名和维度？**
【要点】key = SHA-256(模型名 + 维度 + 内容)。任何一项变化都视为新向量——改维度配置后绝不会误用旧维度的缓存值。value 存 Redis（SET 无过期，嵌入不随时间失效），Redis 挂了降级为直调 API（缓存是优化不是依赖，get/put 全 try-catch）。
【本项目实证】更换向量存储后重索引 1540 块：缓存命中 1540/1540，4.4 秒完成，0 次 API 调用（坑32：分块参数不变时块文本逐字节一致，所以缓存键稳定）。
【追问】为什么不用内容做 key 就够了？→ 同一内容在 512 维和 1024 维下的向量不同，模型升级同理——省钱的缓存如果返回错维度的向量，是比不复用更严重的事故。

**Q2.7 批量嵌入要注意什么？**
【要点】单请求有条数上限 → 批次控制在 16 条；结果按返回的 index 字段归位（不假设返回顺序）；限流错误指数退避；一批失败整体中止入库（宁可让用户重传，不留半份嵌入的文档）。
【本项目实证】1545 块 83 批 43 秒完成。

## 3. 向量存储与 Redis Stack

**Q3.1 ⭐ 向量库选型怎么做的？**
【要点】决策树：组件最少优先 → Redis Stack（compose 换镜像即得 RediSearch，一个组件同时管缓存和向量）；要"生产级向量库"履历 → Milvus（重，多运维一个独立服务，Java SDK 社区版一般）；已有 PG 的团队 → PGVector（本项目已有 MySQL，为向量再引 PG 双库别扭）。
数据量百万块以下三者检索质量无可感知差异，决策因素是运维成本。
【本项目实证】Redis Stack + Jedis 8 直写 FT.CREATE / FT.SEARCH。HNSW（M=16, EF_CONSTRUCTION=200）+ COSINE + FLOAT32。启动即建索引（幂等，环境问题启动时暴露——key/额度/模块缺失当场报错）。
【追问】为什么不用 MySQL 存向量？→ MySQL 无向量索引类型，只能存 JSON 列内存暴力扫——那是 A 块 MVP 故意走的路（先跑通管线，留升级故事）。

**Q3.2 ⭐ 暴力扫 vs HNSW：复杂度对比。千块级暴力扫反而最快，那为什么还要升级？**
【要点】暴力扫 O(N×dim)：千块 × 1024 维 ≈ 150 万次乘加，内存里亚毫秒；十万块级进入数百毫秒，百万块级秒级。HNSW 分层近邻图 + 贪心下行，近似 O(logN)，代价是索引内存、构建时间、近似（非精确 NN）。
实测数字（必须背）：1545 块，HNSW p50=2ms / p95=4ms / p99=12ms；JSON 内存暴力扫 p50=0ms / p95=0ms（预热后），首查 36ms（文件加载）。
**为什么升级**：① 复杂度曲线——每涨一个量级差距拉大十倍，现在 2ms vs 0ms，一亿向量时是"几毫秒 vs 几十秒"；② 数据生命周期解耦——向量库独立于应用进程（重启/多实例/扩容），JSON 文件是单机单进程的孤儿数据。诚实的结论比"快了 X 倍"值钱。
【追问】近似索引会不会丢结果？→ 会（recall < 100%），EF_RUNTIME 调大换召回；本项目评测里 HNSW 与暴力扫分数逐位一致（0.5312/0.4848/0.4647 vs 0.5312/0.4847/0.4647）——千块级近似=精确。

**Q3.3 为什么向量检索不用 Spring Data Redis？**
【要点】Spring Data Redis 封装的是通用 KV/结构操作，没有向量检索抽象（FT.CREATE/FT.SEARCH 是 RediSearch 模块的原生命令）。所以缓存用 Spring Data（StringRedisTemplate），向量检索用 Jedis 直写——两个客户端各干各的，按能力边界选工具。
【追问】Jedis 8 和旧版有什么变化？→ JedisPooled 移除，新入口 RedisClient.builder()（可配 poolConfig）；搜索命令在 UnifiedJedis 一系。踩坑：RediSearch 返回的文档属性一律是 String（NUMERIC 也是），强转 Number 直接 ClassCastException。

**Q3.4 RediSearch 实战有哪几个坑？（展示"我真的调过"）**
【要点】
1. 返回属性全是 String，数值要自己转；
2. KNN 参数走 PARAMS，n 是键值 token 总数（对数×2），手写协议时最易错，Jedis 自动算；
3. TAG 过滤查询里连字符等是查询语法特殊字符——UUID 值必须 `\-` 转义，否则语法错误；
4. COSINE 返回的是距离（1-相似度），应用层做 1-x 换算对齐"越大越相似"的语义；
5. KNN 必须按 vector_score 排序、DIALECT 2。
【追问】向量在 Redis 里怎么存？→ 每块一个 HASH（agentflow:chunk:{uuid}），元数据字段 + FLOAT32 小端字节流；索引按前缀建，HNSW 参数建索引时定死。

**Q3.5 testOnBorrow 解决什么问题？代价是什么？**
【要点】连接池里的连接会被远端关闭（容器重启、网络抖动、空闲超时）——借出一条死连接，第一次使用就报错。testOnBorrow = 借出前先 PING，坏连接当场丢弃重建。代价：每次借出多一次往返（本机 <1ms）。testWhileIdle 是更省的替代（后台定期清），但清不干净借出瞬间的窗口。
【本项目实证】Redis 容器重启后首次检索曾拿到陈旧连接报错，testOnBorrow 治本；容器重启后 AOF 恢复数据完整。

**Q3.6 两种向量存储实现的一致性怎么保证？**
【要点】接口统一语义：replaceDocument = 按文档整体替换（先删同 docId 旧块再写新块）。JSON 实现：内存全量 + 写穿落盘，临时文件 + 原子替换（进程被杀不留半截 JSON）；Redis 实现：pipeline 批量 HSET + 先删后写。删除三处联动：登记册 + 向量块 + 上传原件目录。
【追问】Redis 挂了向量数据会丢吗？→ AOF 持久化（appendonly yes），容器重启完整恢复（实测）；最坏丢 1 秒写入（everysec）。

## 4. 评测（C 块——最能拉开差距的部分）

**Q4.1 ⭐ 评测集怎么建的？为什么用"锚点句"标注？**
【要点】40 条锚定 QA + 3 条陷阱题。每条 QA 记录问题 + 锚点句（答案所在的原文片段）。命中判定 = 检索块文本（空白归一化）包含锚点句。
锚点句的核心价值：**评测与分块策略解耦**——换分块方式后块边界全变，"标注 gold chunk id"的做法直接失效，锚点句依然能判断命中。陷阱题（知识库里没有答案的问题）单独评"诚实拒绝"，不进 Recall。
【追问】锚点句判定有什么偏差？→ 锚点太短时跨边界概率低，对滑窗分块偏友好；空白归一化解决换行拼接问题。语料是自写的（20 节 RAG 工程知识），问题与语料同源——这是有意的可控实验环境，不是对开放语料的泛化评测。

**Q4.2 ⭐ Recall@K 和 MRR@K 分别衡量什么？报一下你的数字**
【要点】
- Recall@K：前 K 个结果覆盖了多少应命中目标——"找没找得到"；
- MRR@K：第一个正确结果的排名倒数之均值——"排得靠不靠前"，考虑排序质量。
数字（干净索引 18 块，40 QA，topK=5）：
| 配置 | Recall@3 | Recall@5 | MRR@5 |
|---|---|---|---|
| 结构感知 + 15% 重叠 | 0.850 | 0.975 | 0.759 |
| 固定滑窗 + 15% 重叠 | 0.925 | 0.950 | 0.755 |
| 固定滑窗 + 0% 重叠 | 0.875 | 0.950 | 0.731 |
| 结构感知 + 0% 重叠 | 0.900 | **1.000** | **0.818** |
top-3 → top-5：Recall 明显升（+0.05~0.10），MRR 不动（排序质量与 K 无关）——生产默认 topK=5。
【追问】为什么不用 nDCG？→ 单一 gold 块场景下 MRR 足够刻画排序质量；多相关块时才需要 nDCG 的分级折损。

**Q4.3 ⭐ 评测发现"预期的提升没出现"，你怎么处理的？（本项目最好的故事）**
【要点】预期"结构感知碾压固定滑窗"，实测同 15% 重叠时基本打平（@5: 0.975 vs 0.950）。没有硬拗，追机制：
- 重叠本身就在修补边界损伤——滑窗切坏的句子被 15% 重叠区完整兜住，两种策略被拉到同一水平；
- 于是做消融：把重叠设为 0。差距立刻拉开——structural@0% 拿到全场最优（1.000/0.818），fixed@0% 排序质量受损（MRR 0.731）；
- 结论修正：结构感知的真实优势是"**不依赖重叠这根拐杖**"——块边界天然落在语义边界上；重叠反而稀释块的主题焦点（对本语料 0% 更优）。
方法论收口：先想清楚机制再谈优化；评测的价值是暴露你以为的因果。
【追问】为什么不干脆把默认重叠改成 0？→ 本语料段落短且结构化好；PDF 连续长段落没有结构信号时，重叠仍是必要的兜底。默认保留 15%，结论写进文档。

**Q4.4 ⭐ 语料稀释是怎么回事？（数字最戏剧性的发现）**
【要点】评测语料（18 块）混着一份 1545 块的模板化干扰语料时，Recall@5 从 0.975 跌到 **0.275**——连锚点句原文直接当查询都排不进 top-8，前排全是模板块（0.64~0.67 分）。
原因：模板小节（"从 X 看性能权衡 / 建议先建立基线再谈优化"）对泛化问题语义极近，嵌入模型给"模板通用性"打高分。
教训：评测必须对齐生产的语料构成；**语料治理（去噪、去重）比调分块参数更杠杆**。
【追问】生产上怎么缓解？→ 混合检索（关键词过滤先缩小范围）、按文档/权限过滤（TAG 过滤）、rerank 精排、语料入库前做相似度去重。

**Q4.5 ⭐ 忠实度怎么评的？LLM-as-judge 有什么坑？**
【要点】忠实度 = 回答是否只由检索资料支撑（有没有编造）。做法：答案 + 所引用块全文一起交 DeepSeek 打 1~5 分，只输出 JSON。
两轮迭代（好故事）：第一轮 4.80/5，排查发现唯一的 1 分是**裁判口径缺陷**——那个问题在 topK=4 没检索到，系统诚实拒绝，裁判把"无有据论断"计了 1 分。拒绝恰恰是忠实的最高体现。修正裁判 prompt（"诚实拒绝判 5 分"）重跑：**5.00/5（20/20，零编造）**。
LLM-as-judge 的已知局限：同生态模型自评有自我偏好，绝对分偏高；严谨做法是换厂商模型当裁判。
【追问】这套评测跑一次多少钱？→ 嵌入有缓存；生成 + 裁判 20 条 ≈ 十万 token 级 ≈ 几毛钱——评测便宜到可以天天跑，这才是"评测驱动"的前提。

**Q4.6 陷阱题是什么？结果如何？**
【要点】3 条知识库里根本没有答案的问题（镜像源、GSoC、作者学历）。期望：明确说"参考资料中没有相关内容"而不是编造。实测 **3/3 诚实拒绝**，零编造。
机制保障：系统提示词里显式写了"资料不足以回答就明确说没有，不要编造"——一句话的提示词 + 评测验证，比事后过滤幻觉便宜得多。

## 5. 工程化、安全与成本

**Q5.1 ⭐ 上游 4xx/5xx 怎么处理成用户能看懂的信息？**
【要点】WebClient 对非 2xx 抛 WebClientResponseException，不拦就落进兜底处理器变成笼统 500。在客户端封装层 onErrorMap 统一翻译：401→key 无效请检查配置；402→余额不足；403→无权限；404→base-url 配置；429→限流稍后重试；5xx→服务端异常。附上第三方原始错误详情（截断 200 字）。
【本项目实证】阻塞路径与 SSE 错误事件同一段文案——一处翻译两条路径受益。坏 key 实测通过。

**Q5.2 SQL 注入防线？**
【要点】所有数据访问走 Spring Data JPA 命名查询/方法名派生查询/JPQL 参数绑定，不拼 SQL 字符串。评测脚本的检索条件也全走 API 参数。

**Q5.3 密钥怎么管理？**
【要点】key 只放 gitignored 的 application-local.yml；属性名与环境变量同名，占位符解析顺序 = 系统环境变量 > 本地文件 > 空默认。这套机制要在"无环境变量"场景专门实测（机器残留变量会掩盖配置不生效）。密钥会无声过期：接新平台先做最小探活（key/额度/端点三件事），再写业务代码。
【追问】误提交了怎么办？→ 第一时间作废重发，而不是删提交（历史里还在）。

**Q5.4 Spring Boot 默认 multipart 限制是多少？踩过什么坑？**
【要点】默认 1MB——一份 530KB 的中文文档 UTF-8 后约 1.4MB 直接 MaxUploadSizeExceededException 落兜底 500。配置 25MB 上限 + 单独的异常处理返回 400 友好提示；业务层另有 20MB 校验（双层：框架挡大头，业务给人话）。

**Q5.5 Redis 用了哪些能力？缓存三大问题（穿透/击穿/雪崩）在你的场景里存在吗？**
【要点】用了：embedding 缓存（STRING）、向量存储（HASH + RediSearch 索引）、AOF 持久化。没用：会话缓存与限流（roadmap 2.7 规划中——诚实说没做）。
三大问题在本场景：穿透（查不存在的 key）——嵌入缓存 key 是内容 hash，未命中就回源 API，天然无危害；击穿（热点 key 过期瞬间打穿）——嵌入缓存不过期，不存在；雪崩（大量 key 同时过期）——同上不存在。真正要防的是"Redis 全挂"：缓存层全部 try-catch 降级为直调 API。
【追问】将来做接口限流选什么算法？→ 单机 Fixed Window 够用但要讲清缺点（窗口边界两倍突刺）；更平滑用滑动窗口/令牌桶。

**Q5.6 这套 RAG 的单次问答成本构成？**
【要点】query embedding（~50 token，有缓存后几乎免费）+ 检索（本机毫秒，可忽略）+ 生成调用（输入 = 系统 prompt + top-5 块 ~2K token + 历史 20 条，输出 = 回答）——生成是常驻大头。"存全部、取最近 20 条"把多轮的输入 token 控制在稳定区间。索引侧成本只在新增内容发生（有缓存兜底）。
【实证】全部实验（1500+ 块索引 + 数百次查询 + 评测）消耗约 10 元以内的 embedding 额度 + 少量 DeepSeek 余额。

## 6. 系统设计延伸（把项目答成设计能力）

**Q6.1 数据量涨到 100 万块，这套架构哪里先崩？怎么演进？**
【要点】顺序：① 单机 Redis 内存先吃紧（1M 块 × 1024 维 × 4B ≈ 4GB + 图结构开销 → 需要独立向量库实例或 Milvus/分片）；② 批量嵌入吞吐（并行批 + 限流退避 + 断点续跑）；③ 检索质量（纯向量 → 混合检索 + rerank）；④ 上传解析变批处理队列。架构红利：VectorStore 是接口，换 Milvus 只加一个实现类。
**Q6.2 多用户/多知识库怎么隔离？**
【要点】每块已带 docId 元数据；扩展：向量库 TAG 加 kbId/ownerId，KNN 查询改过滤式（`@kbId:{x} =>[KNN...]`）——RediSearch 支持过滤+KNN 混合查询；登记表加归属字段，鉴权在 API 层。这正是 roadmap 2.6"kbId"的设计初衷。
**Q6.3 混合检索和 rerank 会怎么加？**
【要点】混合：关键词（RediSearch TEXT/TAG 查询）与向量各召回 top-N，加权融合（或 RRF）——SearchController 里融合两个 VectorStore 查询即可。rerank：粗召回 20~50 条 → 交叉编码器精排取 top-5——加在 RagService.search 的返回前，对外接口不变。诚实说明：本次未实现（可选项），但接口位置和收益（通常大于调块长/topK）讲得清。
**Q6.4 为什么整个管线要做成接口 + 双实现（VectorStore/Chunker）？**
【要点】三个红利：① 升级不动调用方（JSON→Redis，RagService 零改动）；② 评测可以来回切实现跑对比（本次消融实验直接受益）；③ 面试可讲性——每个抽象都有存在的理由，不是教科书式分层。
**Q6.5 Jackson 3 / Boot 4 有什么坑？（展示踩在最新版本上）**
【要点】Boot 4 升级到 Jackson 3（包名 tools.jackson），com.fasterxml 只剩注解兼容包——import 错包编译期才发现；Jackson 3 的解析异常改为非受检（JacksonException extends RuntimeException），catch IOException 直接编译报错（坑23）。WebClient 自动配置在 spring-boot-starter-webclient 而不是 starter-webflux（坑1）。

## 7. 诚实清单（被问到没做的，这样答）

| 未做项 | 回答口径 |
|---|---|
| 混合检索（roadmap 2.5） | 规划内未做；接口位置、融合方式（加权/RRF）、预期收益（报错码类查询）讲得清 |
| Redis 会话缓存 + 限流（2.7） | 同上；Fixed Window 的边界突刺缺点会主动讲 |
| Rerank | 评测可选项未跑；机制（交叉编码器 vs 双塔）与接入位置清楚 |
| 压测（5.4）/ trace（5.1） | Phase 5 后续内容；压测会压 SSE 长连接（首 token 延迟、连接速率），不只 QPS |
| OCR | 扫描件明确报不支持——诚实失败好过静默空结果 |
| 多轮对话里 sources 不落库 | 历史回放看不到卡片；持久化方案（消息表加来源列）想好了，属增量 |

> 通病预防：所有"没做"的答案都以"当前边界 + 下一步 + 为什么这个优先级"收尾，不要只说"没做"。
