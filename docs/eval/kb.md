# AgentFlow 检索增强生成工程手册

本文档是 AgentFlow 项目的知识库评测语料：内容覆盖 RAG（检索增强生成）管线各环节的工程决策，
每节给出可检索的具体事实。评测集（evalset.json）中的问题与"锚点句"均出自本文档。

## 一、分块策略

分块是把解析后的长文本切成适合检索的小块。块长上限设为 400 字符左右时，大多数中文技术文档
能够在语义完整性与检索粒度之间取得平衡。相邻块之间保留 10% 到 20% 的重叠，
可以避免关键句正好落在切块边界上而丢失上下文。

固定滑窗分块不感知任何结构，按固定步长在字符流上滑动切割，实现最简单，
但会把句子和小节拦腰切断。结构感知分块先识别标题与段落边界再装箱，
每个块自带所属小节的标题元数据，检索命中后能直接告诉用户"出自哪个小节"。

锚点句：结构感知分块的块元数据里带有所属小节的标题。

## 二、嵌入模型与维度选择

嵌入模型把文本映射为高维向量，语义相近的文本在向量空间中距离更近。
智谱 embedding-3 模型支持 256、512、1024、2048 四种输出维度，默认 2048 维。
维度越高表达能力越强，但向量存储的内存开销和检索延迟也随之上升：
每个向量的原始存储约等于"维度数乘以 4 字节"。

AgentFlow 选择 1024 维：它处在质量与成本的平衡点，与常见的开源模型 bge-m3 的原生维度一致，
同时把千块级知识库的索引内存控制在几兆字节量级。维度是索引参数的一部分，
一旦建好索引再改维度，所有历史向量都会作废，必须重新嵌入并重建索引。

锚点句：维度是索引参数的一部分，一旦建好索引再改维度，所有历史向量都会作废。

## 三、相似度度量与归一化

余弦相似度衡量两个向量夹角的余弦值，取值范围从负一到一，越大越相似。
检索系统常用的做法是先把向量归一化（模长缩放为一），之后两个向量的点积就等于余弦相似度，
计算可以省去一次模长运算。

RediSearch 的 COSINE 距离返回的是"距离"而不是"相似度"，数值等于一减去余弦相似度，
因此在应用层要做一次一减 X 的换算，让得分语义与自研实现保持一致：越大越相似。

锚点句：数值等于一减去余弦相似度，因此在应用层要做一次一减 X 的换算。

## 四、HNSW 近似最近邻索引

暴力检索对每个查询都要扫过全部向量，复杂度与向量总数成正比，
千块级毫秒完成，十万块级就会进入数百毫秒区间。HNSW（分层可导航小世界图）
通过构建多层近邻图实现近似最近邻搜索，查询从顶层贪心下行，复杂度近似对数级。

HNSW 的关键参数：M 是每个节点的出边数，越大图越密、召回率越高、内存占用越大，
常用值 16；EF_CONSTRUCTION 是建图时候选队列的长度，常用值 200，影响索引质量与构建时间；
EF_RUNTIME 是查询时候选队列长度，运行时调大可以换召回率，代价是延迟上升。
近似索引的代价是结果不是精确最近邻，但在正确调参下召回率可以接近百分之百。

锚点句：EF_RUNTIME 是查询时候选队列长度，运行时调大可以换召回率。

## 五、RediSearch 实战要点

Redis Stack 在原生 Redis 之上附带 RediSearch 模块，支持向量字段的 HNSW 索引与 KNN 查询。
用 Java 接入时 Spring Data Redis 并不封装向量检索，需要用 Jedis 直接发送 FT.CREATE 与
FT.SEARCH 原生命令。建索引时用 PREFIX 前缀限定只索引业务键，向量以 FLOAT32 小端字节流写入 HASH。

实战中容易踩的坑：KNN 查询的参数通过 PARAMS 传递，参数个数写错会直接报语法错误；
TAG 字段的过滤查询里，连字符等符号是查询语法的一部分，UUID 值必须先转义；
搜索结果里的数值字段全部以字符串形式返回，应用层要自己转类型。

锚点句：搜索结果里的数值字段全部以字符串形式返回，应用层要自己转类型。

## 六、嵌入缓存设计

同一文本重复嵌入是纯粹的浪费——分块参数不变时重传文档，块的文本完全一致。
嵌入缓存以"模型名加维度加内容的哈希"作为键，任何一项变化都视为新向量，
避免改配置后误用旧维度的缓存值。缓存写入 Redis，进程重启后依然命中。

这一设计在实测中收益明显：对一份 1540 块的文档更换存储引擎后重新索引，
全部块的嵌入都命中缓存，索引过程只花了四秒多，没有产生任何 API 调用费用。

锚点句：对一份 1540 块的文档更换存储引擎后重新索引，全部块的嵌入都命中缓存。

## 七、批量嵌入与限流

嵌入 API 普遍支持一次请求多条文本，批量可以显著摊薄网络往返开销。
但单请求有条数上限，超过会报错或被静默截断，稳妥的做法是把批次控制在十六条左右，
并按返回结果里的 index 字段把向量归位到输入顺序，不要假设返回顺序与请求顺序一致。

遇到限流错误时应该指数退避后重试，而不是立刻放弃。批量嵌入还要注意失败的中途状态：
一批失败就整体中止入库，宁可让用户重传，也不要留下半份只嵌入了一半的文档。

锚点句：并按返回结果里的 index 字段把向量归位到输入顺序，不要假设返回顺序与请求顺序一致。

## 八、检索评测指标

召回率 Recall@K 衡量前 K 个检索结果覆盖了多少应命中的目标片段，是最基础的检索质量指标。
MRR（平均倒数排名）进一步考虑排序质量：第一个正确结果排第几名，倒数就是几分，
排得越靠前得分越高。两个指标都需要一个事先标注好的评测集。

标注评测集时，为每个问题记录一条"锚点句"（答案所在的原文片段），
评测脚本判断检索结果是否包含锚点句。这种做法的好处是评测与分块策略解耦：
换一种分块方式，块的边界变了，锚点句仍然能判断命中与否。

锚点句：这种做法的好处是评测与分块策略解耦：换一种分块方式，块的边界变了，锚点句仍然能判断命中与否。

## 九、忠实度与 LLM 裁判

检索质量之外，还要评生成质量。忠实度（faithfulness）衡量回答是否只由检索到的资料支撑，
有没有模型自己编造的内容。人工逐条核对成本太高，常用替代是 LLM 裁判：
把回答和它引用的资料一起交给另一个模型，让它按一到五分打分并给出理由。

LLM 裁判的已知局限是自我偏好——同一个模型的输出给自己打分往往偏高，
严谨的做法是换不同厂商的模型当裁判，或在报告中注明这一偏差。

锚点句：严谨的做法是换不同厂商的模型当裁判，或在报告中注明这一偏差。

## 十、混合检索与重排

纯向量检索对精确关键词（产品名、报错码、人名）并不擅长，嵌入模型会把它们"语义化"掉。
混合检索把关键词过滤与向量召回融合：先用倒排或 TAG 过滤缩小范围，再做向量排序，
简单加权融合就能带来可见的提升。

重排（rerank）是第二级精排：先粗召回几十条，再用交叉编码器对"问题-片段"对逐条打分取前列。
交叉编码器比双塔嵌入更准但更慢，所以只对粗排的少量候选使用。重排带来的质量提升
通常大于调整块长或 topK，代价是每次查询多一次模型调用。

锚点句：交叉编码器比双塔嵌入更准但更慢，所以只对粗排的少量候选使用。

## 十一、上下文注入与引用编号

把检索块注入提示词时，每条资料带上编号（如 [1]、[2]），并要求模型在用到资料的句子末尾
标注编号。这让回答的可信度可以被人工抽查：看到引用编号就能定位到原文块。
资料不足以回答时要明确说"参考资料中没有相关内容"，禁止编造——这条指令必须显式写进系统提示。

多轮对话中，检索只用当前问题做查询；历史消息照常拼接在系统提示之后，
这样引用编号始终只对应本轮检索结果，语义不会漂移。

锚点句：资料不足以回答时要明确说"参考资料中没有相关内容"，禁止编造——这条指令必须显式写进系统提示。

## 十二、流式协议设计

服务端推送回答用 SSE（Server-Sent Events）：单向、基于 HTTP、断线可重连，
比 WebSocket 轻得多，适合"请求一次、服务器持续吐字"的大模型对话场景。
浏览器端 EventSource 只支持 GET，对话需要 POST，因此用 fetch 手动读取流并自行拆帧。

自定义 SSE 协议的经验：会话标识先发一个独立事件，客户端不用等流结束就能拿到；
文本增量要做 JSON 编码再发——SSE 规范会吃掉 data 冒号后的一个空格，
而模型输出常常自带前导空格，裸发会丢字符；回答流结束后追加一个来源事件帧，
把本轮命中的资料块与引用编号一起推给前端渲染引用卡片。

锚点句：而模型输出常常自带前导空格，裸发会丢字符。

## 十三、上传解析管线

文档解析推荐 Apache Tika：一套 API 覆盖 PDF、DOCX、TXT 等几十种格式，
按内容探测类型而不是轻信扩展名——把纯文本改名为 .pdf 上传，Tika 仍按纯文本解析成功。
解析大文件时要设置字符数上限并捕获截断异常，超大文档按截断处理并如实告知。

扫描版 PDF 的文字在图片里，纯解析抽不出文本，需要 OCR，属于另一条管线。
解析完成后建议把上传原件落盘保存：向量库损坏时可以用原件重新索引，这是"可重建"的底气。

锚点句：扫描版 PDF 的文字在图片里，纯解析抽不出文本，需要 OCR，属于另一条管线。

## 十四、向量库选型

个人项目选向量库的决策树：组件最少优先，选 Redis Stack——compose 里换个镜像就得到
RediSearch，一个组件同时承担缓存与向量检索；要"生产级向量数据库"的履历就上 Milvus，
代价是多运维一个独立服务；已有 PostgreSQL 的团队选 PGVector 最顺手，但要为新项目单独引入
双数据库就别扭了。数据量在百万块以下时，三者的检索质量没有可感知差异，决策因素主要是运维成本。

无论选哪个，向量检索都必须走向量库而不是内存暴力扫——不是为了眼前的延迟数字，
而是为了复杂度曲线：暴力扫是线性，索引是对数，数据量每涨一个量级差距就拉开十倍。

锚点句：暴力扫是线性，索引是对数，数据量每涨一个量级差距就拉开十倍。

## 十五、失败路径与降级

管线组件的依赖要有降级设计：嵌入缓存挂了就当缓存未命中，检索照跑；
Redis 不可用时 embedding API 直调，只损失命中率不损失功能。上传到一半失败
（比如嵌入服务超时）时不要留下半份入库的文档：先落原件、再解析、再嵌入、最后一次性入向量库，
任何一步失败都中止并且不登记文档，用户重传即可，不会产生检索脏数据。

错误信息要给人看：第三方返回 401 时，提示应该是"key 无效请检查配置"，
而不是笼统的内部错误。在客户端封装层统一翻译上游错误码，阻塞接口和流式接口两条路径同时受益。

锚点句：先落原件、再解析、再嵌入、最后一次性入向量库，任何一步失败都中止并且不登记文档。

## 十六、密钥与配置管理

API 密钥只放在被 gitignore 的本地配置文件里，任何脚本不得把密钥写进日志或测试。
配置文件里的属性名与环境变量同名，占位符解析顺序是：系统环境变量优先，
其次本地配置文件，最后空默认值。这套机制要在"无环境变量"的场景下专门实测一次，
因为机器上残留的旧变量会掩盖配置不生效的问题。

密钥会在无声无息中过期：接入新平台时先做一次最小探活调用，确认 key、额度、端点三者都正常，
再开始写业务代码，能省掉大量排查时间。

锚点句：接入新平台时先做一次最小探活调用，确认 key、额度、端点三者都正常，再开始写业务代码。

## 十七、提示词工程的工程化

系统提示词是管线的一部分，改动要过评测：一句话的措辞变化可能让引用率大幅波动。
把提示词放进版本控制，评测脚本固定评测集与指标口径后再对比提示词版本，
才能归因到"是提示词变好了，而不是检索变了"。

少示例（few-shot）对格式遵循有帮助：在系统提示里放一个带引用编号的示例回答，
模型输出引用格式的稳定性显著提升。提示词长度与费用直接相关，注入的资料块不是越多越好——
块数增多会稀释注意力，也让无关内容有机会混进回答。

锚点句：把提示词放进版本控制，评测脚本固定评测集与指标口径后再对比提示词版本，才能归因到"是提示词变好了，而不是检索变了"。

## 十八、成本核算

大模型应用的成本要按"每次问答的全链路"核算：嵌入调用、检索基础设施、生成调用的输入输出
token 都要计入。嵌入只在新内容出现时发生且有缓存兜底，生成调用才是每次问答的常驻成本。
把历史消息拼进上下文时，"存全部、取最近 N 条"的策略能在多轮对话里把输入 token
控制在一个稳定区间，N 取二十左右在记忆效果与费用之间是常见选择。

锚点句：N 取二十左右在记忆效果与费用之间是常见选择。

## 十九、并发与长连接

大模型对话是典型的长连接 IO 密集场景：一次请求占用连接几十秒，线程模型下很容易把线程池占满。
虚拟线程适合这类场景——阻塞等待时不占平台线程。压测要压 SSE 长连接而不只是普通短请求，
观察指标除了 QPS 还要看连接建立速率、首 token 延迟和错误率。

对上游模型调用要做信号量限流与超时降级：超过并发上限直接返回兜底文案，
不要让请求无限排队，排队超过用户耐心等于失败。

锚点句：压测要压 SSE 长连接而不只是普通短请求，观察指标除了 QPS 还要看连接建立速率、首 token 延迟和错误率。

## 二十、评测驱动的迭代节奏

没有评测集的优化都是凭感觉。正确的节奏是：先固定评测集与指标，跑出基线数字；
每次只改一个变量（分块策略、topK、提示词），跑同一评测集对比；数字提升才合入，
不提升就回退并记录原因。评测集要留一部分"陷阱题"——知识库里根本没有答案的问题，
检验系统会不会诚实地说"没有相关内容"。

锚点句：评测集要留一部分"陷阱题"——知识库里根本没有答案的问题，检验系统会不会诚实地说"没有相关内容"。
